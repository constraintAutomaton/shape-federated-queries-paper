\section{Shape-Guided Federation}\label{sec:approach}

We propose \emph{Shape-Guided Federation}, an approach that replaces the costly custom summaries
used by HiBISCuS and FedUP with RDF data shapes, which are increasingly published alongside
SPARQL endpoints and offer greater expressiveness at no additional construction cost.
We first describe the content of the federation members with a shape index in \cref{sec:summaries},
then present \ac{SASS}, our shape-aware adaptation of FedUP's result-aware source-selection
algorithm, in \cref{sec:sass}.
We then compare the expressiveness of shape indexes with the summaries of prior approaches in \cref{sec:expressiveness}.
Finally, we discuss how shape indexes can be published by data providers or extracted by third parties to deploy Shape-Guided Federation in \cref{sec:deployment}.

\subsection{Endpoint Summaries via RDF Data Shapes}\label{sec:summaries}

The HiBISCuS algorithm~\cite{saleem2014hibiscus} proposes a summary approach, later refined by FedUP~\cite{aimonierdavat:hal-04538238}, to improve federated query performance.
These summaries are \acp{KG} that, for each endpoint, characterize the predicates available for \ac{RDF} terms with respect to the endpoint's \emph{authority}\footnote{The authority as defined by the \href{https://datatracker.ietf.org/doc/html/rfc3986}{Uniform Resource Identifier (URI): Generic Syntax} specification.} in its \acp{IRI}.

We propose a different summarization approach, based on \ac{RDF} data shapes.
At an abstract level, HiBISCuS-type summaries already capture structural regularities of endpoint data, and \ac{RDF} shape languages provide a standard mechanism to represent this structure.
We therefore use \ac{RDF} data shapes to obtain a reusable and more expressive alternative to the custom summaries used by HiBISCuS and FedUP.

Independently of the shape language, we abstract a shape using three definitions,
first a target in \cref{def:target},
then the triple constraints on the entities it selects in \cref{def:triple-constraint},
and finally a shape in \cref{def:shape}.

\begin{definition}[Target]\label{def:target}
A target is a function $t : \mathcal{G} \to 2^{\mathcal{I}\mathcal{B}}$ that selects, from a \ac{KG}, the \acp{IRI} and blank nodes to be described, which we call \emph{entities}.
\end{definition}

\begin{definition}[Triple constraint]\label{def:triple-constraint}
Let $t$ be a target.
A triple constraint for $t$ is a triple $(p, C_O, r)$ constraining, in a \ac{KG} $G$, the triples $(x, p, o) \in G$ whose subject $x$ is in $t(G)$, where $p$ is a predicate,
$C_O$ is either
(i) a constraint on the value of the object of $p$, or
(ii) a reference $@s'$ to a shape $s'$, requiring the object of $p$ to conform to $s'$,
and $r \in \{\mathit{true}, \mathit{false}\}$ states whether $p$ is required.
\end{definition}

\begin{definition}[Shape]\label{def:shape}
A shape is a pair $s = (t, \mathit{TC})$, where
$t$ is a target as defined in \cref{def:target}, and
$\mathit{TC} = \{A_1, \dots, A_k\}$ is a set of alternatives, each alternative $A_j$ being a set of triple constraints for $t$ as defined in \cref{def:triple-constraint}.
Given a \ac{KG} $G$, a term $o$ satisfies $C_O$ if it satisfies the value constraint of kind~(i), or conforms to $s'$ when $C_O = @s'$.\footnote{Shapes can refer to each other cyclically, for instance a shape for persons whose \texttt{foaf:knows} objects are persons.}
An entity $x \in t(G)$ satisfies a triple constraint $(p, C_O, r)$ if the object of every triple $(x, p, o) \in G$ satisfies $C_O$
and, when $r = \mathit{true}$, $G$ contains at least one such triple.
The entity $x$ conforms to $s$ if, for some alternative $A_j \in \mathit{TC}$, it satisfies every triple constraint of $A_j$
and the object $o$ of every triple $(x, p, o) \in G$ satisfies $C_O$ for some $(p, C_O, r) \in A_j$.
\end{definition}

To describe the content of each federation member, we use a summary method called \emph{shape index}~\cite{tam2025},
``a mapping between \ac{RDF} document sets and \ac{RDF} data shapes that describes a subweb controlled by a data provider''~\cite{tam2025},
where a subweb is ``a (sub)\ac{DKG} defined by the \ac{KG} derived from a set of \acp{IRI} controlled by a data provider''~\cite{tam2025}.
A shape index is defined as

\begin{equation}\label{eq:shape-index}
  SI = \{ s_1 \mapsto \mathit{IRI}_1, s_2 \mapsto \mathit{IRI}_2, \dots, s_n \mapsto \mathit{IRI}_n \}
\end{equation}

where $s_i$ is a shape and $\mathit{IRI}_i = SI(s_i)$ is a set of \acp{IRI}, and it is \emph{complete} when every shape $s_i \in \mathrm{dom}(SI)$ is closed~\cite{tam2025}.

In a federation, a subweb is a set of federation members, identified by the \acp{IRI} of their SPARQL endpoints.
Each $\mathit{IRI}_i$ is thus the set of all endpoint \acp{IRI} whose \ac{KG} contains triples of an entity conforming to $s_i$.
The mapping $s_i \mapsto \mathit{IRI}_i$ therefore states that the entities selected by the target of $s_i$, together with their triples constrained by the alternatives of $s_i$, are stored in the endpoints of $\mathit{IRI}_i$,
whereas the objects of these triples that must conform to a shape $s'$ through a triple constraint of kind~(ii) \emph{can be described} by the endpoints of $SI(s')$.
In most cases, $\mathit{IRI}_i$ contains a single endpoint.
It can however contain several, for instance when data following the same schema are partitioned over multiple endpoints and the constraints of $s_i$ do not distinguish the partitions.

We further require the shape index to describe every triple of the endpoints it maps.
Let $\mathit{KG}(e)$ be the \ac{KG} of the endpoint identified by the \ac{IRI} $e$, and
$G_{SI} = \bigcup_{e \in E_{SI}} \mathit{KG}(e)$, with $E_{SI} = \bigcup_{s_i \in \mathrm{dom}(SI)} \mathit{IRI}_i$,
the \ac{KG} of the subweb described by $SI$.
Conformance to the shapes of $SI$ is evaluated over $G_{SI}$,
so an entity whose triples are stored in several endpoints conforms to a shape only if all its triples in the federation satisfy it.
A triple $(x, p, o)$ is \emph{described} by a shape $s_i = (t_i, \mathit{TC}_i)$ if $x \in t_i(G_{SI})$, meaning that its subject is selected by $t_i$ over this subweb,
and $s_i$ accepts the predicate $p$, meaning that $(p, C_O, r) \in A$ for some alternative $A \in \mathit{TC}_i$, some $C_O$, and some $r$.
The shape index must satisfy
\begin{equation}\label{eq:coverage}
  \forall e \in E_{SI},\ \forall (x, p, o) \in \mathit{KG}(e),\ \exists s_i \in \mathrm{dom}(SI) :
  e \in \mathit{IRI}_i \land (x, p, o) \text{ is described by } s_i.
\end{equation}
Shape languages also allow open shapes, which accept any predicate not forbidden by a negative constraint.
Open shapes satisfy \cref{eq:coverage} trivially but describe little about the data.
We therefore only consider closed shapes, as captured by \cref{def:shape}, and thus complete shape indexes.

Closed shapes also determine where the triples of an entity are stored.
Each data provider describes its own subweb,
so an entity whose triples are split over the subwebs of several providers would require a closed shape over data that no single provider controls.
We therefore assume \emph{entity locality}, meaning that the triples of an entity accepted by a shape are stored in the endpoints of that shape,
\begin{equation}\label{eq:locality}
  \forall s_i \in \mathrm{dom}(SI),\ \forall x \in t_i(G_{SI}) :
  \{ (x, p, o) \in G_{SI} \mid s_i \text{ accepts } p \} \subseteq \bigcup_{e \in \mathit{IRI}_i} \mathit{KG}(e).
\end{equation}
The triples of an entity can thus be split over several endpoints of $\mathit{IRI}_i$,
whereas the triples whose subject is an object of this entity conforming to a nested shape can be stored in the endpoints of other shapes.

Shape languages can express exclusive unions between sets of triple constraints, which \cref{def:shape} captures with the alternatives of $\mathit{TC}$.
By \cref{def:shape}, an entity conforming to a shape $s = (t, \mathit{TC})$ satisfies an alternative $A_j \in \mathit{TC}$,
and each of its triples uses a predicate of a triple constraint of $A_j$.
A shape index therefore describes not only which predicates occur in an endpoint, but also which combinations of predicates a single entity can have.

\lstinputlisting[caption={ShEx example with an exclusive choice of user name representation.},label={lst:user-alt}]{code/user_alt.shex}

For example, consider the ShEx shape in \cref{lst:user-alt}.
It describes users that must have a \texttt{foaf:mbox} and either:
\begin{itemize}
  \item a \texttt{foaf:name}, or
  \item a \texttt{foaf:givenName} and a \texttt{foaf:familyName}.
\end{itemize}

Since \texttt{ex:UserShape} is closed, a user conforming to it follows exactly one of these alternatives.
Hence, if \texttt{ex:UserShape} is mapped to a set of endpoint \acp{IRI} in a shape index, the index describes that no user stored in these endpoints has both a \texttt{foaf:name} and a \texttt{foaf:givenName}.
Different users may nevertheless follow different alternatives, so the endpoints can contain users of both kinds.

Beyond the combinations of predicates that an entity can have, triple constraints also describe the objects of these predicates,
either by constraining their value, kind~(i), or by requiring them to conform to another shape, kind~(ii).



\lstinputlisting[caption={ShEx example using object constraint.},label={lst:shex-object-constraint}]{code/object_constraint.shex}

For instance, in \cref{lst:shex-object-constraint}, the triple constraints
\texttt{(rdf:type, [foaf:Person foaf:User], true)}, \texttt{(foaf:name, LITERAL, true)}, and
\texttt{(foaf:mbox, IRI, false)} of \texttt{ex:UserShape}, and
\texttt{(foaf:name, xsd:string, true)} of \texttt{ex:Hobby}, are of kind~(i),
as they constrain the value of the object,
meaning that users are of type \texttt{foaf:Person} or \texttt{foaf:User}, their name is a literal, their mailbox is an \ac{IRI}, and hobbies have a name of type \texttt{xsd:string}.
In contrast, \texttt{(ex:hobby, @ex:Hobby, true)} is of kind~(ii),
as it requires the object of \texttt{ex:hobby} to conform to \texttt{ex:Hobby}.
All these triple constraints are required, except \texttt{(foaf:mbox, IRI, false)},
since the \texttt{?} of \cref{lst:shex-object-constraint} makes the mailbox optional,
so a user may have no mailbox, but any mailbox it has is an \ac{IRI}.
Mapped to a set of endpoint \acp{IRI} in a shape index, these triple constraints thus describe not only the predicates of the users stored in these endpoints, but also their objects.

By describing the objects of the triples, triple constraints also describe which endpoints can share terms,
since the object of a triple stored in one endpoint can occur, as a subject, predicate, or object, in the triples stored in another endpoint.
We capture this with the notion of link.

\begin{definition}[Link]\label{def:link}
Let $SI$ be a shape index and $(p, C_O, r)$ a triple constraint of a shape $s_i \in \mathrm{dom}(SI)$.
The triple constraint $(p, C_O, r)$ is \emph{compatible} with a shape $s_k = (t_k, \mathit{TC}_k) \in \mathrm{dom}(SI)$
if there exist a \ac{KG} $G$ in which every triple is described by a shape of $SI$ and a term $o$ satisfying $C_O$
such that $o$ occurs in a triple of $G$ described by $s_k$,
either as its subject, with $o \in t_k(G)$,
as its predicate, with $(o, C, r') \in A$ for some $A \in \mathit{TC}_k$,
or as its object, with $o$ satisfying $C$ for some $(q, C, r') \in A$ and $A \in \mathit{TC}_k$.
The endpoints linked by $(p, C_O, r)$ are
$\mathit{link}(p, C_O, r) = \bigcup \{ SI(s_k) \mid s_k \in \mathrm{dom}(SI) \text{ compatible with } (p, C_O, r) \}$.
\end{definition}

For instance, let $s_u$ and $s_h$ be the shapes \texttt{ex:UserShape} and \texttt{ex:Hobby} of \cref{lst:shex-object-constraint}.
The triple constraint \texttt{(ex:hobby, @ex:Hobby, true)} of $s_u$ is compatible with $s_h$ as a subject,
so the endpoints of the users are linked to the endpoints $SI(s_h)$ of the hobbies.
The triple constraint \texttt{(rdf:type, [foaf:Person foaf:User], true)} is compatible only with shapes in which \texttt{foaf:Person} or \texttt{foaf:User} can occur,
for instance as the object of another \texttt{rdf:type} constraint.
In contrast, \texttt{(foaf:mbox, IRI, false)} is compatible with every shape in which an \ac{IRI} can occur,
and \texttt{(foaf:name, LITERAL, true)} only with shapes having an object constraint satisfied by a literal, since a literal can be neither a subject nor a predicate.

except the values listed by \texttt{ex:category}, which are kept.
In the refined summary, each alternative of \texttt{ex:UserShape} has its own node,
so no node has both a \texttt{foaf:name} and a \texttt{foaf:familyName},
and the object of \texttt{ex:member} becomes both \texttt{ex:UserShape\_alt1} and \texttt{ex:UserShape\_alt2}.

\begin{definition}[Summary of a shape index]\label{def:summary}
Let $SI$ be a shape index.
Each shape $s_i = (t_i, \mathit{TC}_i) \in \mathrm{dom}(SI)$ has a set of nodes $N_i \subseteq \mathcal{I}$,
which is $N_i = \{ s_i \}$ in the \emph{coarse} summary.
In the \emph{refined} summary, $N_i = \{ s_i \}$ if $\mathit{TC}_i$ has a single alternative,
and $N_i = \{ n_{i,j} \mid A_j \in \mathit{TC}_i \}$, with one fresh \ac{IRI} per alternative, otherwise.
Each triple constraint $\tau = (p, C_O, r)$ of $SI$ has a fresh \ac{IRI} $\iota_\tau$, called its identifier.
The summary of $SI$ maps each shape to a \ac{KG},
$\Psi(SI) = \{ s_i \mapsto S_i \mid s_i \in \mathrm{dom}(SI) \}$,
where $S_i$ contains a triple $(n, p, o)$ for every node $n \in N_i$,
every triple constraint $\tau = (p, C_O, r)$ of an alternative of $n$,
and every $o \in \mathit{obj}(\tau)$, with $\mathit{obj}(\tau)$ being
(i) $N_k$ when $C_O = @s_k$,
(ii) the listed terms when $C_O$ lists the allowed values, and
(iii) $\{ \iota_\tau \}$ otherwise.
\end{definition}

Each term of a summary stands for a set of terms of the federation, called its \emph{extension}.
The extension of a node $n \in N_i$ is the set of entities conforming to $s_i$, or to the alternative of $n$ in the refined summary,
the extension of an identifier $\iota_\tau$ is the set of terms satisfying the $C_O$ of $\tau$,
and the extension of a listed term is the term itself.
Two terms of the summaries \emph{match} if their extensions can intersect over a \ac{KG} in which every triple is described by a shape of $SI$, as in \cref{def:link}, which a solver decides from the shapes.
In particular, two nodes match if an entity can conform to both, which requires each to accept the predicates the other requires.
For instance, \texttt{ex:l1} and \texttt{ex:l5} match, since a literal of type \texttt{xsd:string} satisfies both \texttt{LITERAL} and \texttt{xsd:string},
whereas \texttt{ex:l4} and \texttt{"game"} do not, since \texttt{"game"} is not an integer,
and \texttt{ex:UserShape} and \texttt{ex:ClubShape} do not, since a club has an \texttt{ex:practices} that the closed shape of users does not accept.

We call our approach \emph{\ac{SASS}}: a result-aware source-selection procedure that operates over an \ac{SGSC} rather than a plain HiBISCuS-type summary.
To position SASS with respect to prior work, we first restate the Result-Aware source-selection procedure used in FedUP.
\Cref{alg:fedup-result-aware} is reproduced from FedUP (Algorithm 1)~\cite{aimonierdavat:hal-04538238}.

\begin{algorithm}
  \caption{Result-Aware source-selection procedure reproduced from FedUP (Algorithm 1)~\cite{aimonierdavat:hal-04538238}.}\label{alg:fedup-result-aware}
  \begin{algorithmic}[1]
    \Function{A}{$Q, F$}
      \State \Return $\fmu(A'(Q, F))$
    \EndFunction
    \Function{$A'$}{$Q, F$}
      \State $\Phi_o \gets \emptyset$
      \If{$Q$ is a triple pattern $\mathrm{tp}$}
        \State $\Phi_o \gets \Phi_o \cup \{\freq_{\mathrm{tp}}^{f} \mid f \in F\}$
      \ElsIf{$Q$ is $(P_1 \Join P_2)$}
        \State $\Phi_1, \Phi_2 \gets A'(P_1, F), A'(P_2, F)$
        \State $\Phi_o \gets \Phi_o \cup \{\fmj(\{\varphi_1, \varphi_2\}) \mid \varphi_1 \in \Phi_1 \land \varphi_2 \in \Phi_2\}$
      \ElsIf{$Q$ is $(P_1 \cup P_2)$}
        \State $\Phi_1, \Phi_2 \gets A'(P_1, F), A'(P_2, F)$
        \State $\Phi_o \gets \Phi_o \cup \{\varphi \mid \varphi \in \Phi_1 \lor \varphi \in \Phi_2\}$
      \ElsIf{$Q$ is $(P_1 \leftouterjoin P_2)$}
        \State $\Phi_1, \Phi_2 \gets A'(P_1, F), A'(P_2, F)$
        \For{$\varphi_1 \in \Phi_1$}
          \State $\Phi_{\mathrm{join}}^{\varphi_1} \gets \{\varphi_2 \mid \varphi_2 \in \Phi_2 \land \sols(\fmj(\{\varphi_1, \varphi_2\})) \neq \emptyset\}$
          \If{$\Phi_{\mathrm{join}}^{\varphi_1} = \emptyset$}
            \State $\Phi_o \gets \Phi_o \cup \{\varphi_1\}$
          \Else
            \State $\Phi_o \gets \Phi_o \cup \{\fleftjoin(\varphi_1, \fmu(\Phi_{\mathrm{join}}^{\varphi_1}))\}$
          \EndIf
        \EndFor
      \ElsIf{$Q$ is $(P \text{ FILTER } R)$}
        \State $\Phi \gets A'(P, F)$
        \State $\Phi_o \gets \Phi_o \cup \{\ffilter_{R}(\varphi) \mid \varphi \in \Phi\}$
      \EndIf
      \State \Return $\{\varphi \mid \varphi \in \Phi_o \land \sols(\varphi) \neq \emptyset\}$
    \EndFunction
  \end{algorithmic}
\end{algorithm}

The $\sols(\varphi)$ function evaluates query plan $\varphi$ against a HiBISCuS-type summary,
returning the bag of results it produces.
The goal of the result-aware source-selection algorithm is to generate an exhaustive set of
relevant query plans and to evaluate each plan over the summary to determine which federation
members cannot produce results for it.

We propose to replace $\sols(\varphi)$ with $\sols_{\mathrm{SGSC}}(\varphi)$ throughout this algorithm.
This modification is necessary because our proposed summary is not a \ac{KG}; it is an
exclusive union of \ac{SGSC} branches, each paired with a shape constraint.

\Cref{alg:sols-sgsc} presents $\sols_{\mathrm{SGSC}}(\varphi)$.
The idea is to iterate over every branch of the exclusive union in $S$ and check whether that
branch alone can answer the query derived from $\varphi$.
For this purpose, we extend the signature of $\sols$ to $\sols(\varphi, S)$, where $S$ is the set of
\ac{KG} instances over which the query is evaluated.
The helper function $\mathrm{constraint}$ collects all \texttt{FILTER} expressions from the query plan into
a single conjunctive expression; it also rewrites each ground term (IRI or literal) in a triple
pattern into a fresh variable and adds an equality filter between that variable and the original term.

In \cref{alg:sols-sgsc}, the condition $r_{\mathrm{bag}} \neq \emptyset \land C \land k$ has two purposes.
First, $r_{\mathrm{bag}} \neq \emptyset$ confirms that evaluating $\varphi$ against branch $\mathrm{kg}$ yields at
least one result on the summary.
Second, the conjunct $C \land k$ checks whether the shape constraints $C$ of the branch are
satisfiable together with the filter expression $k$ derived from $\varphi$.
A branch that fails this satisfiability check is pruned: even if it produces results on the
summary, those results cannot satisfy the query's filter constraints given the shape of the data.

\begin{algorithm}
  \caption{$\sols_{\mathrm{SGSC}}(\varphi, S)$ determines whether a query plan $\varphi$ can be answered by any member of the federation.}\label{alg:sols-sgsc}
  \begin{algorithmic}[1]
    \Function{$\sols_{\mathrm{SGSC}}$}{$\varphi, S$}
      \For{$\mathrm{kg} \mapsto C \in S$}
        \State $r_{\mathrm{bag}} \gets \sols(\varphi, \mathrm{kg})$
        \State $k \gets \mathrm{constraint}(\varphi)$
        \If{$r_{\mathrm{bag}} \neq \emptyset \land C \land k$}
          \State \Return $r_{\mathrm{bag}}$
        \EndIf
      \EndFor
      \State \Return $\emptyset$
    \EndFunction
  \end{algorithmic}
\end{algorithm}

\paragraph{Soundness}
\ac{SASS} preserves the soundness guarantee of FedUP~\cite{aimonierdavat:hal-04538238}:
if $\sols_{\mathrm{SGSC}}(\varphi, S) = \emptyset$, then no member of the
federation can produce a non-empty result for $\varphi$.
This follows from the \ac{SGSC} definition: by construction, every endpoint's data
conforms to at least one branch $\mathrm{kg} \to C$ in $S$.
If every branch fails the condition $r_{\mathrm{bag}} \neq \emptyset \land C \land k$, then no conforming
endpoint can satisfy both the structural requirements of $\varphi$ and its filter constraints,
and the federation engine may safely prune this plan.

\subsection{Deploying Shape-Guided Federation}\label{sec:deployment}
